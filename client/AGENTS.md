# AGENTS.md — 小红书克隆（Android 客户端 + mockserver）

## 仓库地图

- `client/app/` Android 客户端（Kotlin + Compose 单模块）。
- `client/mockserver/` Node mock server（REST + `/ws/chat`，唯一 npm 依赖 `ws`）。
- `client/docs/` 三份活文档，改动对应内容时必须同步：
  - **API契约-v2.md** — 接口行为的唯一权威（含 WS 帧 §12.7、客户端行为约定 §12.8）。
  - **客户端架构与开发规范.md** — 目录职责 §2、硬性规范 §4、交付自检清单 §8（改代码前后都看）。
  - **交付说明-*.md** — 每轮交付的范围与「已知取舍」记录。

## 可维护性约定（防腐蚀纪律）

1. **注释只写 Why**：约束、决策、反直觉的故意为之（例：`RealtimeConnection` 的
   「静默＝不触发登录失效」）。What/How 复述代码的注释删掉。注释引用稳定锚点
   （`G5-2`、`I1`、`契约 §12.7` 这类编号）——编号比机制描述活得久；机制参数
   （间隔秒数、实现方式）由代码和命名常量自述。
2. **改机制先 grep 词汇**：改动或删除一个机制时，先用该概念的词 grep 全仓库
   （代码 + 注释 + 三份文档），把陈旧引用一并清理。注释和文档会静默腐烂，
   grep 是唯一的兜底手段。
3. **文档同变**：行为变更的同一批提交里更新契约、架构规范与受影响的交付说明；
   行为级取舍（删机制、换方案）记入交付说明「已知取舍」，写清放弃了什么、换到了什么。
4. **一个概念一个词**：同一概念在代码、注释、文档里只用同一个词，保证第 2 条
   grep 得全。已知易撞词：`Session` = 登录态（`SessionManager`），
   `Conversation` = 聊天会话（IM）——中文都叫「会话」，勿混用。
5. **语义放进被检查的载体**：领域数值写成命名常量并在注释标契约锚点
   （例：`PING_INTERVAL_MS` → §12.7）。能进名字、类型、常量的语义就不写进注释——
   名字腐烂时编译器会报警，注释腐烂时无人知晓。
